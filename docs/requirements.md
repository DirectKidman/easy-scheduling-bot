# Discord イベント管理bot 要件定義

更新: 2026-09-30（ホスティングを Cloudflare Workers + D1、HTTPインタラクション方式（ゲートウェイ不使用）に確定。実装言語を TypeScript に確定）

## 1. 目的

Discord の中だけでイベントの作成・参加確認・確認ができる bot を自作する。

- サーバー主が導入し、イベント作成は運営側（サーバー主・運営ロール）が行う
- 参加者はボタンで回答する
- 参加者は `/my` で、bot を導入しているサーバーをまたいで「自分の予定」を確認できる
- 外部サービスへの誘導（Web フォーム、外部ページ）は発生させない

## 2. スコープ

### 対象

- サーバーインストール型の通常 bot
- **HTTPインタラクション方式**（Discord が HTTP で送ってくるインタラクションを受ける。ゲートウェイの常時接続は使わない）
- 確定型イベント（日時が決まっているイベントの告知と出欠）
- `/my` による自分の予定の横断表示
- 運営者向けの設定コマンド

### 対象外（初期）

- ゲートウェイ常駐（24時間稼働サーバー）。コマンド以外のイベント（bot 外し、メッセージ削除など）の通知は受けず、定期ジョブで確認しに行く（6 章）
- メッセージ内容の読み取り（特権インテント。チャットの文章に反応する機能はすべて対象外）
- Discord 標準のスケジュールイベントの取得・連携
- ユーザーアカウントのトークンを使った取得（セルフボット。規約違反のため行わない）
- 他人が運営する別 bot（Apollo, Sesh など）のデータ取得
- E2EE（告知が Discord 上で平文のため効果が薄い。保存量の最小化と説明の透明性で対応する）
- ユーザーインストール型アプリ対応（要検証項目が多いため後回し）
- 候補日の投票（日程調整）モード → フェーズ3

## 3. 運用前提

- bot はサーバー主が管理権限で招待する
- イベントの作成・編集・確定・削除は運営者のみ
- 参加ボタンと `/my` と `/forget` は全員が使える
- bot の運営者（ホストする人）は、DB の内容を技術的に読める。これを隠さず、導入時に説明する

## 4. 機能要件

### 4.1 コマンド

| コマンド | 実行者 | 内容 |
|---|---|---|
| `/setup` | サーバー主（管理権限） | 運営ロール、告知チャンネル、サーバーのタイムゾーンを設定 |
| `/event` | 運営者 | モーダルでイベント作成 → 告知メッセージを投稿 |
| `/my` | 全員 | 自分の予定を、導入済みの全サーバー横断で一覧表示（自分にだけ見えるメッセージ） |
| `/forget` | 全員 | 自分の回答を削除（範囲選択あり。5.3 参照） |

権限は、コマンド登録時の `default_member_permissions` に加えて、**ボタン押下時にも bot 側で毎回権限チェック**する（ボタンが見えないことに頼らない）。

### 4.2 告知メッセージ（1イベント = 1メッセージ）

```
📅 読書会
日時　<t:1760266800:F>（<t:1760266800:R>）
場所　#voice-1
主催　@主催者

✅ 参加 (3)　@a @b @c
🤔 未定 (1)　@d
❌ 不参加 (0)

[✅ 参加] [🤔 未定] [❌ 不参加] [⋯ 詳細]
```

- 日時は `<t:UNIX秒:F>` / `<t:UNIX秒:R>` で書き、閲覧者のローカル時間に自動変換させる
- 回答ボタンを押すたびに、DB の状態からメッセージを再生成して更新する（連打しても食い違わないように）
- 参加者が多い場合は「他n人」と省略し、「詳細」ボタンで全員を表示する
- 名簿のメンションは通知を飛ばさない形（埋め込み内）にする

### 4.3 `/my` の表示

```
📋 あなたの予定
サーバーA　10/11(土) 19:00　読書会　✅
サーバーB　10/12(日) 14:00　ボドゲ会　🤔
```

- 自分にだけ見えるメッセージで返す（永続しない。クライアント再起動で消える。編集できるのはインタラクショントークンの有効な15分間のみ）
- 通常のサーバーインストールだけだと DM では使えない。いずれかのサーバーのチャンネルで実行する前提
- 他サーバーのサーバー名・イベント名を表示するかは、ユーザー設定でオフにできるようにする（後回し可）

### 4.4 リマインド

- 前日と当日に、告知チャンネルへ投稿（定期ジョブから REST API で投稿）
- DM 通知は、相手が DM を閉じていると失敗するため、失敗時はチャンネル投稿に落とす
- 定期ジョブが止まっていた・失敗した場合に備え、「送信済み」の印を DB に持ち、次回実行時に送れていない分を拾い直す（何度実行しても二重送信にならないこと）

## 5. データ要件

### 5.1 スキーマ（概要）

```
servers   : guild_id, 告知チャンネルID, 運営ロールID, タイムゾーン, 削除予定日時（nullable）
events    : id, guild_id, message_id, タイトル, 開始日時（UTC）, 状態, リマインド送信済み印
responses : event_id, user_id, 状態（参加/未定/不参加）, 更新日時
```

- 日時は **UTC で保存**。サーバーのタイムゾーンは入力の解釈にだけ使う
- タイトルは `/my` のために保存する（割り切り）。それ以外のデータ保存は最小限にする
- `responses.event_id` は `ON DELETE CASCADE` にして、イベント削除時に回答が連動して消えるようにする（D1 上で外部キー制約と CASCADE が期待どおり動くことを最初に確認する）

### 5.2 削除ポリシー

| 契機 | 消すもの | タイミング |
|---|---|---|
| 時間経過 | 終了後30日を過ぎたイベントと回答 | 毎日1回の定期ジョブ |
| ユーザー操作 | 自分の回答 | `/forget` 実行時 |
| bot がサーバーから外された | そのサーバーの設定・イベント・回答 | 定期ジョブで検知して印を付け、猶予期間（7〜30日）後に削除 |

- 物理削除とする（削除フラグだけで残さない）
- bot 外しは、ゲートウェイのイベントではなく**1日1回の定期ジョブ**で確認する。各サーバーに REST API で問い合わせ、アクセスできなければ `servers.削除予定日時` に印を付ける。猶予中に再び到達できるようになったら印を外す（一時的な障害による誤検知対策）
- メンバーがサーバーを抜けた場合の追跡は行わない。保存期間の経過で消える
- バックアップの保持期間は短く（目安30日）し、「バックアップからは最大N日で消える」と説明に明記する
- ログにはイベント内容や回答内容を出さない

### 5.3 `/forget` の仕様

実行すると、自分にだけ見える確認画面で範囲を選ぶ。

| 選択肢 | 消すもの | 進行中・今後の予定への影響 |
|---|---|---|
| 過去分だけ（既定） | 終了済みイベントの回答 | なし |
| すべて | 全サーバー分の回答 | 参加予定・投票中の回答も消える |
| 特定のイベント（フェーズ3） | 選んだ1件の回答 | そのイベントの集計だけが変わる |

- 「すべて」は、確認画面に影響を受ける未来・進行中のイベント一覧を具体的に出し、[キャンセル]/[削除する] の確認ボタンを付ける
- 「不参加」は回答として残り、「削除」は行を消して「未回答」に戻る。別物として扱う
- 削除後、影響を受けた未来・進行中のイベントのメッセージを再描画する
- 確定済みイベントの回答を消しても、確定した日時は変えない

```sql
-- 過去分のみ
DELETE FROM responses
WHERE user_id = ?1
  AND event_id IN (SELECT id FROM events WHERE start_at < unixepoch());

-- すべて
DELETE FROM responses WHERE user_id = ?1;
```

（D1 は SQLite 系。日時の持ち方に合わせて条件式は調整する）

## 6. アーキテクチャ・運用要件

### 6.1 構成

- ホスティング: **Cloudflare Workers**（HTTPインタラクション）+ **D1**（DB）+ **Cron Triggers**（定期ジョブ）
- 実装言語: **TypeScript**
- Discord の開発者ポータルで「Interactions Endpoint URL」に Worker の URL を登録する
- 受信したリクエストは、**Ed25519 署名を毎回検証**する（Discord の仕様。検証に失敗したら 401 を返す）
- スラッシュコマンドの登録は、Worker のデプロイとは別に、登録用のスクリプトかエンドポイントを用意して実行する（コマンドを追加・変更するたびに再登録が必要）
- 告知メッセージの投稿・更新、リマインド投稿は、bot トークンを使った REST API で行う
- ボタンは、`custom_id` にイベントIDと操作を埋め込み、受信のたびに DB を見て処理する（常駐サーバーがないので、状態はすべて DB に置く）
- 機密情報（bot トークン、公開鍵など）は Workers のシークレット機能で管理し、リポジトリには入れない

### 6.2 定期ジョブ（Cron Triggers）

| ジョブ | 頻度の目安 | 内容 |
|---|---|---|
| リマインド | 短い間隔（1時間ごとなど。制限は要確認） | 送信時刻を過ぎたイベントのリマインドを投稿し、送信済みの印を付ける |
| 時間経過の削除 | 1日1回 | 終了後30日を過ぎたイベントを削除 |
| bot 外しの確認 | 1日1回 | 各サーバーへの到達可否を確認し、削除予定の印を付ける／外す／期限が来たら削除 |
| 告知メッセージの存在確認 | 1日1回 | DB のメッセージIDが Discord 上に存在するか確認し、消されていたらイベントの状態を更新 |

### 権限とセキュリティ

- bot の権限は最小限（メッセージ送信、埋め込み、スラッシュコマンドなど）。**メッセージ内容インテントとメンバーインテントは使わない**
- 確定・編集・削除の権限チェックは、サーバー側で毎回行う

### 信頼性

- インタラクションには **3秒以内に応答**する。重い処理は先に「処理中」の応答を返し、後からフォローアップで結果を返す（インタラクショントークンの有効期間は15分）
- メッセージ更新は、短時間の連打をまとめてレート制限を避ける
- 定期ジョブは冪等にする（途中で失敗しても、再実行で二重に処理されない）
- Workers の実行時間・リクエスト数の制限に収まるよう、多数のサーバーを処理するジョブは分割する
- DB のバックアップ手段を、D1 の提供機能を調べたうえで早めに決める（定期エクスポートを外部に保存する案も検討）

### プライバシー

- 保存するのは、参加状態、ユーザーID、イベントのタイトルと日時程度
- 導入時に、何を保存し、誰が見られるか（bot 運営者は技術的に読める）を、短い文章で示す
- 公開して他人に使ってもらう場合は、プライバシーポリシーと利用規約を用意する。個人情報保護法の扱いは、専門家または公式情報で確認する（実装側では法的判断をしない）

## 7. フェーズ分け

### フェーズ1（MVP）

- Worker のセットアップ（署名検証、コマンド登録、D1 のマイグレーション）
- `/setup`、`/event`（確定型）、参加3ボタン
- `/my`（横断表示）
- 時間経過の削除（定期ジョブ）と `ON DELETE CASCADE`
- 権限チェック、UTC 保存

### フェーズ2

- `/forget`（過去分／すべて）
- リマインド（定期ジョブ、DM フォールバック、送信済み印による取りこぼし対応）
- bot 外しの確認ジョブ（猶予期間付き削除）
- 告知メッセージの存在確認ジョブ

### フェーズ3

- 日程調整（候補日の投票）モードと「確定する」操作
- 特定イベントの回答削除
- `/my` で他サーバー名を隠す設定
- 匿名化（ユーザーIDだけ外して人数を残す）
- 公開向けの整備（ポリシー、規模に応じた運用の見直し）

## 8. 実装前に小さく確認すること（未検証事項）

1. Workers で HTTP インタラクションを受け、署名検証を通してボタン押下時にメッセージを更新できること、押したユーザーIDが取れること
2. bot が外されたサーバーに対する REST API の応答（到達不可を判定できるエラーか）と、誤検知の頻度
3. Cloudflare Workers / D1 / Cron Triggers の料金、無料枠、実行時間・リクエスト数・実行間隔の制限（公式ページで最新を確認）
4. D1 での外部キー制約と `ON DELETE CASCADE` の挙動、マイグレーションの運用、バックアップ手段
5. DM でのリマインドが、インストール方式によって変わらないか
6. `/my` を DM でも使いたい場合、ユーザーインストールを併用する必要があるか
7. Discord のデベロッパーポリシーにあるデータ取り扱い・削除要件

## 10. 参考にした前提

- スケジュールイベントの取得 API は bot 権限のみで、OAuth2 のユーザートークンでは使えない（公式ディスカッションでの記述。現行仕様は公式ドキュメントで確認すること）
- 自分にだけ見えるメッセージは、操作したユーザーと bot にだけ見える。サーバー主や他メンバーには見えない
- ユーザーインストール型アプリは `applications.commands` スコープのみで、サーバー・DM の情報は取得できない
- HTTP で受ける bot は、ゲートウェイ（WebSocket）の常時接続を使わないため、Cloudflare Workers のようなサーバーレスと相性が良い。コマンド以外のイベントが必要ならゲートウェイ側で別途受ける（併用も可能）
- メッセージ内容の読み取りは特権インテント。使わない場合、メッセージ内容の欄は空で届く
